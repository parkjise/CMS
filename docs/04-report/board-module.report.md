## 1. 개요

### 1.1 목표

고객(소상공인)이 **자기 손으로** 홈페이지에 게시판을 운영하게 한다.
예를 들어 병원은 공지와 소식, 펜션은 객실 소개와 후기, 회사는 채용 공고를 직접 올릴 수 있어야 한다.

이번 보고서가 다루는 범위는 기획안 v2.2 중 지금 구조에 맞게 받은 부분이다.

- 게시판 설정 (정렬, 페이지당 글 수, 검색 노출)
- 입력 칸 관리 (기본값, 목록 표시, 연락처 · 이메일 · 링크 칸)
- 디자인 (목록형 · 갤러리형 · FAQ형 · 카드형)
- 카테고리 (글을 분류하는 1단계 분류)
- 권한 (회원만 읽기, 회원도 글쓰기)
- 운영 설정 (비밀글, 새 글 알림, 비회원 글쓰기, 신고)
- 마무리 보완 (갭 분석에서 찾은 문제 수정)

### 1.2 기간과 범위

- **기간**: 2026-11-05 ~ 2026-11-06
- **태스크**: T-146 ~ T-152 (9개 태스크, 9개 PR)
- **기반**: T-139 ~ T-144 (공지 실사용, 게시판 추가, 테마형 화면, 칸 빌더, 본문 편집기 등)가 먼저 끝나 있어야 했다.
- **기준 문서**: `docs/CMS_Board_Module_Spec_v1.1.md` (기획서 v1.1), `TASK.md` Phase 18

모든 PR은 CI (백엔드, 프런트엔드, 전체 화면 시험)가 모두 통과한 뒤에만 머지했다.
DB 변경과 권한 변경이 들어간 PR은 사용자가 "머지해줘"라고 승인한 뒤에만 머지했다 (운영 규칙 CLAUDE.md 12.8).

### 2.2 고객이 할 수 있게 된 일

- 게시판마다 **목록 · 갤러리 · FAQ · 카드** 중 모양을 고르고, 정렬과 페이지당 글 수를 정한다.
- 분류(카테고리)를 만들어 글을 나누고, 홈페이지에서 분류 탭으로 걸러 본다.
- 회원만 글을 읽게 하거나, 회원이 직접 글을 쓰게 한다.
- 비회원도 이름과 글 비밀번호로 글을 쓰게 할 수 있다 (병원 업종은 막혀 있음).
- 비밀글을 허용하고, 새 글이 올라오면 알림을 받는다.
- 방문자가 글을 신고하면 관리자가 처리한다.

### 2.3 쓸 수 없게 막아 둔 것 (안전 장치)

- 병원 업종은 방문자 글쓰기를 쓸 수 없다 (의료법 관련 위험, 결정 D-14).
- 공지 게시판(기본 게시판)은 권한 · 운영 설정을 바꿀 수 없고, 비밀글도 만들 수 없다.
- 필수 칸이 있는 게시판은 방문자 글쓰기를 켤 수 없다 (서버에서 막음, 409 응답).

## 3. 설계 대비 일치율과 의도적 후속 작업

### 3.1 일치율

갭 분석 (설계 문서와 실제 코드를 비교하는 검사)을 두 가지 기준으로 했다.

| 기준 | 일치율 | 해석 |
|------|--------|------|
| 조정된 범위 (기획서 v1.1 + 결정 D-13) | **약 93%** | 이번에 하기로 한 것은 거의 다 만들었다 |
| 원본 기획안 v2.2 전체 | 약 45% | 나머지는 일부러 미룬 큰 기능들이다 |

원본과의 차이는 **실수로 빠진 것이 아니다.** 아래 항목은 결정 D-13에 따라 뒤로 미뤘다.

### 3.2 의도적으로 뒤로 미룬 기능 (D-13)

| 미룬 기능 | 이유 |
|-----------|------|
| 사이트 선택 · 사이트 번호 구분 | 계정 하나에 사업체 하나라서 필요 없다 |
| 초안 · 발행 · 버전 · 되돌리기 · 실시간 미리보기 | 지금은 저장하면 바로 홈페이지에 나온다. 큰 작업이라 뒤로 미룸 |
| 승인 흐름, 편집자 역할 | 지금 역할은 관리자와 보기 전용뿐 |
| 조회수 | 우선순위 낮음 |
| 댓글, 첨부 파일 | 파일은 비공개 저장소가 필요해서 별도 작업 |
| 게시판 종류별 기본 칸 자동 넣기 (BM-02) | 후속 과제로 남김 |

### 3.3 갭 분석에서 찾은 실제 문제와 수정 (T-152)

| 번호 | 문제 | 수정 |
|------|------|------|
| 1 | 홈페이지에 [글쓰기] 버튼이 나오는데 실제로는 막혀 있던 경우가 있었다 | 실제로 열리는지 기준으로 값을 내보내고, 막힌 곳에는 버튼을 그리지 않음 |
| 2 | 공지 게시판의 운영 설정과 비밀글을 화면에서만 막고 서버는 허용했다 | 서버에서도 막음 (409 응답) |
| 3 | 이전 · 다음 글을 찾으려고 게시판의 글 번호를 전부 읽었다 | 데이터베이스 창 함수로 두 개만 가져오도록 변경 |
| 4 | 글 비밀번호 틀림 횟수를 글마다 따로 셌다 | 사업체와 IP 단위로 함께 셈 (같은 IP가 여러 글을 돌아가며 시도해도 막힘) |
| 5 | 방문자 글쓰기의 reCAPTCHA (사람 확인 장치) 검사에 그 폼 전용 확인 값이 없었고, Google 장애 때 안내가 없었다 | 그 폼 전용 검사 이름을 확인하고, 장애 시 안내 (503) |
| 6 | 기획서와 작업 목록이 실제 코드와 어긋남 | 문서를 코드에 맞춤 |

### 4.2 화면 확인 방식

- 화면이 바뀐 PR(T-146 ~ T-151-B)은 **개발용 DB 사본**에 붙여 실제 화면으로 확인했다. 확인 뒤 사본은 삭제했다. T-152 는 화면 코드가 바뀌지 않아 서버 시험으로 확인했다.
- 확인 기기는 PC와 휴대폰 두 가지.
- 테마형 템플릿 화면은 화면으로는 확인하지 못했다. 시험 계정이 코드형 템플릿(hospital-a)을 쓰고 있어서 **단위 시험으로만** 확인했다.

### 4.3 화면 확인 중 찾아 머지 전에 고친 버그

| 태스크 | 버그 | 상황 |
|--------|------|------|
| T-149 | 분류 탭 간격이 맞지 않음 | 화면 확인 중 발견 |
| T-151-A | 로그인 링크의 돌아올 주소가 서버와 화면에서 다르게 만들어져 경고 발생 (hydration 오류) | 화면 확인 중 발견 |
| T-151-B | 비회원 글 삭제 시 비밀번호 칸이 가로로 전체 폭까지 늘어남 | 화면 확인 중 발견 |

### 4.4 테스트에 대한 메모

- 서버 시험이 실제로 확인하는 것: 로그인 없음 (401), 관리자 토큰 · 다른 사업체 회원 토큰 · 보기 전용 계정 (403), 남의 글 · 회원 글 · 관리자 글을 비회원 비밀번호로 열기 (404), 입력 오류 (400), 1시간 한도 · 비밀번호 틀림 한도 (429), 사업체 분리를 DB 에서 직접 확인 (RLS).
- 비밀글 · 회원만 읽기는 "목록 · 상세 · 서버가 그린 페이지 · 사이트맵 어디에도 내용이 없다"를 시험과 실제 화면 양쪽에서 확인했다.

## 5. 보안 요약

| 영역 | 적용한 장치 |
|------|-------------|
| 사업체 분리 | 모든 게시판 · 글 테이블에 사업체 번호를 두고, 데이터베이스 행 수준 보안(RLS)을 적용. 다른 사업체의 글 번호로 접근하면 404 |
| 회원만 읽기 | 서버가 회원 토큰을 확인 (없음 401, 관리자 · 다른 사업체 토큰 403). 응답은 저장되지 않게 설정 |
| 검색 · 사이트맵 제외 | 회원만 읽기 게시판, 비밀글, 검색 노출을 끈 게시판은 검색엔진 색인과 사이트맵에서 뺌 |
| 비밀글 | 목록에는 제목과 자물쇠만, 상세는 쓴 회원 또는 관리자만. 홈페이지 서버에는 잠긴 상태만 전달 |
| 비회원 글 비밀번호 | 암호화(bcrypt)해서 저장. 이름만 함께 저장하고 IP 주소는 저장하지 않음 |
| 비밀번호 시도 제한 | 사업체 안에서 같은 IP가 10분에 5번 틀리면 (여러 글을 돌아가며 시도해도 함께 셈) 맞아도 잠시 막음. 제한 저장소가 없으면 거절 (맞히기보다 막는 쪽 우선) |
| 글쓰기 제한 | 회원은 1시간에 10개, 비회원은 같은 IP에서 1시간에 5개. 사람 확인(reCAPTCHA v3)은 그 폼 전용 |
| 신고 | 같은 사람은 한 글에 한 번만 신고 가능. 신고자 정보는 해시로만 기록하고 원본 IP · 회원 번호는 남기지 않음. 같은 IP는 1시간에 10번까지 |
| 감사 기록 | 게시판 설정 변경, 권한 변경, 신고 처리를 감사 로그에 남김 (글 본문과 IP는 남기지 않음) |
| 본문 입력 | 서버가 허용 목록으로 다시 만들어 위험한 링크 · 그림 주소를 거부. 스크립트는 실행되지 않음 |

### 5.1 알려진 보안 한계

- **관리자 비밀글의 사진**은 지금 공개 저장소(누구나 주소로 열 수 있음)에 있다. 비공개 저장소는 후속 작업이다.
- **IP 제한은 Nginx가 전달한 주소를 믿는다.** 백엔드는 반드시 Nginx 뒤에 있어야 한다. 그렇지 않으면 IP 제한을 우회할 수 있다.

## 6. 남은 위험과 오픈 전 할 일

### 6.1 남은 위험

| 위험 | 내용 | 대응 |
|------|------|------|
| 신고 악용 | 글이 신고 3건이면 자동으로 숨겨진다. 서로 다른 IP 3곳이면 누구든 아무 글이나 숨길 수 있다 | 관리자가 다시 공개할 수 있음. 기준 (3건) 조정은 후속 과제 |
| IP 제한 우회 | 위 5.1 참조 | 백엔드를 Nginx 뒤에만 두기 |
| 법률 | 병원 후기는 의료법 제56조(치료 경험담 광고 금지)에 걸릴 수 있음 | 병원 업종 차단은 이미 적용. 전문가 확인 필요 |
| 법률 | 개인정보 수집 고지 문구 | 전문가 확인 필요 |
| 법률 | 권리 침해 신고 접수와 게시 중단 절차 | 절차 문서 준비 필요 |

### 6.2 오픈 전 할 일

1. **법률 확인** (위 6.1의 세 가지). 방문자 글쓰기를 실제 고객에게 열기 전에 끝내야 한다.
2. **백업 체계 (B5)**: 아직 해결되지 않았다. 운영 전 필수.
3. **이미지 저장소 (B6)**: 지금 이미지는 익명 읽기 공개 저장소에 있다. 오픈 전에 S3 방식 전환을 권장한다.
4. **BM-02 칸 기본 세트**: 게시판 종류별 기본 칸은 아직 없다. 오픈 필수는 아니지만 고객 편의를 위해 검토.

### 6.3 참고

- 오픈 목표는 2027년 4월 말이다. 이 전제가 바뀌면 옛 공지 옮기기 등 "옮길 데이터가 없다"는 가정을 다시 확인해야 한다.

## 7. 배운 점

- **기획안을 그대로 받지 않고 현재 구조에 맞춰 나눈 것이 효과가 컸다.** 원본은 약 45%만 맞았지만, 받기로 한 범위는 약 93%를 맞췄다.
- **화면 확인을 PR마다 한 것이 버그를 잡았다.** 자동 시험은 통과했지만 화면에서 간격 · 경고 · 입력칸 폭 문제가 나왔다.
- **"화면에서 막았다"와 "서버에서 막았다"는 다르다.** 갭 분석에서 화면만 막고 서버는 허용한 곳이 여러 군데 나왔다. 앞으로는 서버 검사를 먼저 만든다.
- **테스트 계정이 한 가지 템플릿만 써서 다른 템플릿 화면을 못 봤다.** 템플릿마다 확인 계정이 필요하다.
- **DB · 권한 변경 PR은 사용자 승인 뒤에만 머지하는 규칙**을 지켰다 (CLAUDE.md 12.8).
