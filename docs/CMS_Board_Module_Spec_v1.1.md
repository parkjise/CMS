## 0. 문서 목적 및 근거

본 문서는 기존 CMS를 유지하면서, 비개발자 관리자가 **게시판을 직접 생성·복제·비활성화·삭제하고, 게시판 필드를 추가·수정·관리하며, 게시판을 홈페이지에 연결**할 수 있는 독립 모듈을 설계한다.


- 본 문서의 **신규 권고/제안**은 기존 CMS에서 구현 완료되었다는 의미가 아니다. 실제 코드와 최종 API/DB 모델은 구현 착수 전 대조해야 한다.

- 2026-11-05 코드 대조: 1 ~ 3장 · 5 ~ 11장의 **[현행]** 표기는 `main`(T-138 머지 시점) 코드를 읽어 확인했다. 운영 환경 재현은 아니다.

### 구분 원칙
- **[현행]** 기존 CMS 기획서에 기술된 현재 구조와 구현 메모.
- **[1 ~ 4단계]** 우선 개발할 새 기능 (3장 표).
- **[후속 P1·P2]** 4단계 뒤에 검토할 기능.
- **[결정 필요]** 제품 정책 또는 개발팀 합의가 필요한 항목.

## 1. 프로젝트 개요

### 1.1 문제 정의

현재 CMS는 섹션 편집과 업종별 템플릿 운영에 강점이 있다. 그러나 게시판을 고객마다 자유롭게 늘리고, 각 게시판의 입력 필드를 달리하는 **범용 게시판 빌더**가 필요하다.

| 사용자 불편 | 개선 목표 |
|---|---|
| 새 게시판을 만들 때 개발자 작업에 의존 | 관리자에서 3단계로 생성 |
| 업종마다 필요한 입력 항목이 다름 | 필드 빌더에서 추가·변경 |
| 게시글 수정과 게시판 설정이 혼재 | 게시판 설정 / 콘텐츠 운영 분리 |
| 설정 실수로 데이터가 손실될 수 있음 | 소프트 삭제·이력·복구 |
| 만든 게시판을 홈페이지에 연동하기 어려움 | 기존 섹션 편집에서 게시판 선택·배치 |

### 1.2 핵심 원칙

1. **노코드 운영:** 사용자는 DB/JSON/코드를 알 필요가 없다.
2. **게시판 정의와 콘텐츠 분리:** 게시판 자체의 설정과 게시글 운영을 분리한다.
3. **기존 CMS 호환:** 기존 `BOARD`, `NOTICE_LATEST`, `inquiries` 흐름을 단계적으로 연동한다.
4. **안전한 스키마 변경:** 필드 변경 시 기등록 데이터가 사라지지 않아야 한다.
5. **테넌트 격리:** 모든 조회·수정·파일 접근에 테넌트와 권한 검증을 적용한다.
6. **점진적 확장:** 처음에는 게시판/필드/게시글 CRUD에 집중하고 AI·자동화는 후속 개발한다.

### 1.3 주요 이용자

| 역할 | 주요 작업 |
|---|---|
| 테넌트 최고 관리자 | 게시판 생성·삭제, 필드·권한·표시 설정 |
| 콘텐츠 운영자 (P1 — 지금 역할은 `TENANT_ADMIN` · `TENANT_VIEWER` 뿐) | 게시글 작성·수정·발행, 댓글/신고 처리 |
| 사이트 방문자·회원 | 권한에 따라 글 열람·작성·답변·파일 다운로드 |
| 슈퍼 어드민 | 테넌트 지원·시스템 운영·감사 (정책에 따라 제한) |

## 2. 기존 CMS 연동 현황

### 2.1 현행 사항 — 기존 문서 기준

| 항목 | 현행 구조 / 명시 내용 | 신규 모듈 적용 방향 |
|---|---|---|
| 관리자 | React 19 + Vite + TypeScript | 같은 앱에 메뉴·화면 추가 |
| 고객 사이트 | Next.js 15 | 동적 게시판 렌더러 연동 |
| API | FastAPI, 관리자/공개 API 분리 | 게시판 관리자 API·공개 API 추가 |
| DB | PostgreSQL + RLS | 테넌트별 게시판 테이블 추가 |
| 스토리지 | MinIO/S3 — **이미지만 WebP 로 저장, 버킷은 익명 읽기 공개**, 저장 용량 한도 있음 | 이미지는 재사용. 일반 파일 · 비공개 파일은 별도 버킷 필요 (P1) |
| 섹션 | `sections.page_key`, 섹션별 설정. **코드형 템플릿 · FREE · BASIC 은 섹션 추가 불가** | 기본 게시판은 기존 `BOARD` 섹션으로, 새 게시판은 메뉴로 연결 (5.3) |
| 홈페이지 주소 | 코드형은 매니페스트 페이지만, 주소 3단계까지. **테마형은 한 페이지뿐이고 게시판 섹션 없음** | `/{slug}/b/{게시판}/{글}` 전용 경로 (2단계), 테마형 화면 (3단계) |
| 메뉴 | 코드형 `menu.json` · 테마형 홈 섹션에서만 후보를 만듦 | 게시판을 메뉴 후보에 추가 (2단계) |
| 필드 검증 선례 | `services/inquiry_fields.py` — 칸 정의대로 값 검사 · 정의 밖 값 버림 | 필드 빌더 검증의 출발점 (4단계) |
| 본문 | 공지 샘플은 블록 JSON. 정화 규칙(`rich_text.py`)은 인라인 태그만 허용, 본문 에디터 없음 | Tiptap 노드 JSON 으로 변경, 이전 형식도 읽음 (T-143, 8.2) |
| 사이트맵 | 메인 주소 하나뿐 | 게시판 · 글 주소 추가 (2단계) |
| 공지사항 | `BOARD` 섹션의 `settings` JSON `items` | 신규 `board_posts`로 단계적 이전 |
| 상담 게시판 | `inquiries.is_board` + 공개 상담 API | 당장 유지, 새 모듈과 연결하는 호환 계층 |
| 예약 | `inquiries` 예약 유형 활용 | 별도 도메인으로 유지, 필요 시 게시판처럼 표시 |
| 방문자 인증 | CMS 기획서 섹션 16 | 글쓰기·비밀글 권한에 재사용 |

**주의:** 기존 기획서는 2026-10-25에 공지 데이터를 섹션 JSON으로 저장하도록 결정했다. 본 기획서의 별도 `board_posts` 도입은 그 결정을 **신규 모듈의 범용화 관점에서 변경 제안**하는 것으로, 기존 코드를 곧바로 교체한다는 뜻이 아니다.

### 2.2 호환 전략

**전제: 오픈 전(목표 2027-04 말)이라 옮겨야 할 실제 고객 공지가 없다.** 그래서 v1.0 의 점진 이전 · 이전 도구 · 롤백 절차는 두지 않는다. 오픈 뒤 이 결정을 다시 쓰면 안 된다.

1. 실제 글은 처음부터 `boards` / `board_posts` 에 저장한다 (상위 기획서 오픈 이슈 #27 을 변경).
2. **샘플 글은 지금처럼 섹션 JSON 에 둔다.** 공개 글이 없으면 샘플을 보여 주고, 글을 처음 **공개**하면 공지 · 최신 공지 섹션의 샘플 칸을 빈 목록으로 바꾼다 (임시저장으로는 샘플이 내려가지 않는다). 그 뒤로는 글을 모두 지워도 샘플이 되살아나지 않는다. 공개 글이 생기기 전에 샘플을 내리려면 [샘플 글 지우기] 를 쓴다. 템플릿 미리보기 · 샘플 안내 개수 · 상담 게시판의 `sample_posts` 와 같은 방식이라 `board_posts.is_sample` 은 두지 않는다.
3. `NOTICE_LATEST` 도 같은 규칙으로 실제 최신 글을 읽는다 — 지금은 글 목록을 따로 갖고 있어 공지와 내용이 어긋난다.
4. 상담 · 예약은 현행 `inquiries` 흐름(인증 · 알림 · reCAPTCHA)을 유지하고 이전하지 않는다.
5. 기존 공지 URL 의 샘플 id(`n1` 등)는 실제 글에서 UUID 로 바뀐다. 오픈 전이라 넘겨주기(redirect)는 두지 않는다.

## 3. 기능 범위 및 우선순위

**결정 (2026-11-05): 글쓰기 먼저, 필드 빌더는 뒤로.** 소상공인에게 먼저 필요한 것은 공지를 쓰는 일이고, 필드 설계는 어려운 작업이다. 데이터 모델은 처음부터 `custom_data` 를 두어 뒤에 다시 만들지 않는다.

| 단계 | 태스크 | 범위 | 끝나면 |
|---|---|---|---|
| **1. 공지 실사용 ✅** | T-139 | 게시글 테이블, 글 쓰기 · 수정 · 삭제 · 복원 · 고정 · 공개 여부, 공지 페이지 · 메인 최신 공지 연결, 샘플 전환, 홈페이지 [글쓰기] 버튼 | 고객이 공지를 직접 쓴다 |
| **2. 게시판 추가** | T-140-A ~ C | 게시판 생성 · 복제 · 휴지통, 목록 · 갤러리 · FAQ, `/b/` 경로, 메뉴 연결, 요금제 제한, 사이트맵, 글 일괄 처리 | 공지 외 게시판을 만든다 |
| **3. 테마형 표시 ✅** | T-141 | 테마형 템플릿의 게시판 화면 | 모든 템플릿에서 보인다 |
| **4. 필드 빌더** | T-142-A · B | 필드 정의 · 변경 정책 · 글쓰기 폼 자동 생성 · 평점 등 타입 | 입력 칸을 바꾼다 |
| **기획안 v2.2 ✅** | T-146 ~ T-152 | 정렬 · 글 수 · 검색 노출, 필드 기본값 · 타입, 디자인 · 카드형, 카테고리, 권한(회원만 읽기 · 회원 글쓰기), 운영 설정(비밀글 · 새 글 알림 · 비회원 글쓰기 · 신고) | 방문자가 쓰고 고객이 운영한다 |
| **후속 (P1)** | 미정 | 댓글, 일반 · 비공개 파일, 콘텐츠 운영자 역할, 예약 발행, 자동 저장, 버전 이력, Q&A | |
| **후속 (P2)** | 미정 | 업종별 프리셋, AI 글쓰기, 승인 흐름, 다국어, 분석, 웹진 · 1:1 | |

**전체 완료 기준:** 관리자가 게시판을 만들고 → 필드를 추가하고 → 글을 작성하고 → 홈페이지에서 조회하고 → 게시판/필드를 비활성화·복구할 수 있다.

**현재 범위:** 게시판 생성 · 설정 · 휴지통(T-140-A), 코드형 템플릿(hospital-a)의 새 게시판 화면 · 메뉴(T-140-B), 전체 글 · 사이트맵 · 감사 로그(T-140-C), 테마형의 새 게시판 화면(T-141), 필드 빌더 · 자동 글쓰기 폼 · 공개 표시(T-142-A · B), 본문 편집기(T-143), 다른 사업체 계정 버튼 정리 · 고객 도메인 확인(T-144), 기획안 v2.2 반영(T-146 ~ T-151-B: BM-08 ~ BM-11)과 마무리 보완(T-152)까지 구현했다. 테마형에 공지 전용 페이지는 없다. 기본 게시판을 비활성화하면 샘플도 비우고, 공지 페이지는 빈 안내로 남는다 — 메뉴 숨김은 메뉴 설정에서 한다.

## 4. 메뉴 구조와 권한

왼쪽 메뉴 `게시판 관리` 를 누르면 2뎁스(게시판 목록 · 게시판 생성 · 전체 글)가 펼쳐지고, 게시판 설정과 글 운영의 동선을 나눈다. 기능 플래그 `BOARD_MANAGER`(전 요금제 기본 켜짐)로 메뉴와 API 를 함께 제어한다 — 꺼도 공개 홈페이지는 그대로다 (T-138 원칙).

```text
게시판 관리 (왼쪽 메뉴 — 눌러서 펼침, 그 안의 화면이면 펼친 채로)
├── 게시판 목록 (/admin/boards) — [게시판 추가] 버튼, 휴지통 링크
├── 게시판 생성 (/admin/boards/new) — 추가할 수 없는 요금제는 요금제 안내, 보기 전용 계정은 안내
├── 전체 글 (/admin/posts)
├── 신고된 글 (/admin/posts/reports) — 처리하지 않은 신고가 있는 글 (T-151-B)
└── 게시판 상세 (목록에서 게시판을 눌러 들어감) — 탭
    ├── 글 관리 (/admin/boards/:boardId/posts)
    ├── 기본 정보 (/settings) — 이름 · 설명 · 검색 노출 · 복제 · 휴지통
    ├── 필드 관리 (/fields) — 새 게시판만
    ├── 게시판 디자인 (/design) — 표시 유형 · 유형별 표시 · 정렬 · 글 수 (T-148)
    ├── 카테고리 (/categories) — 1단계 분류 · 순서 · 숨김 · 삭제 시 글 옮기기, 새 게시판만 (T-149)
    ├── 권한 (/permissions) — 글 읽기 누구나 · 회원만 (T-150-A), 글쓰기 관리자만 · 회원도 (T-150-B), 새 게시판만
    ├── 운영 설정 (/operation) — 비밀글 허용 · 새 글 알림 (T-151-A), 비회원 글쓰기 (T-151-B), 새 게시판만
    └── 홈페이지 연결 (/connection) — 주소 · 사용 여부 · 메뉴 표시
```

**메뉴 원칙 (2026-11-05 결정):** 기능이 있는 탭만 연다 — "준비 중" 탭을 두지 않는다. 게시판 추가는 왼쪽 메뉴 [게시판 생성] 과 목록의 버튼 두 곳에서 들어간다 (FREE · BASIC 은 눌러도 요금제 안내, T-146 변경). 고객에게 "배포"는 낯선 말이라 "홈페이지 연결"로 쓰고, 디자인도 지금은 유형뿐이라 여기에 합친다. 태블릿(아이콘 메뉴) · 휴대폰(더보기)은 2뎁스 없이 게시판 목록으로 가고, 전체 글은 목록의 버튼으로 간다.

| 동작 | `TENANT_ADMIN` | `TENANT_VIEWER` | 방문자 |
|---|---|---|---|
| 게시판 · 글 조회 (관리자) | 가능 | 가능 | 불가 |
| 게시판 · 글 쓰기 · 수정 · 삭제 | 가능 | 불가 (T-130 쓰기 차단 그대로) | 게시판이 `회원도` 쓰기면 로그인한 회원이 글쓰기 · 자기 글 수정 · 삭제 (T-150-B). 비회원 글쓰기는 T-151 |
| 공개 글 읽기 | 가능 | 가능 | 가능 (게시판이 `회원만` 이면 로그인한 방문자 회원만, T-150) |

**요금제 (D-01 결정):** FREE · BASIC 은 기본 게시판의 글만 관리, STANDARD 는 게시판 5개까지 추가, PREMIUM 은 제한 없음. 내려도 있던 게시판 · 글은 유지하고 새로 만들기만 막는다 (고객 도메인 T-137-C 와 같은 원칙). 글 수 제한은 두지 않고 저장 용량 한도를 그대로 쓴다.

## 5. 주요 사용자 시나리오

### 5.1 새 게시판 생성

1. `[게시판 관리] → [게시판 추가]` 클릭
2. **기본 정보:** 게시판 이름과 URL 슬러그 입력(중복·예약어 검사)
3. **유형 선택:** 목록/갤러리/웹진/FAQ/Q&A/1:1 중 선택
4. **운영 설정:** 읽기 권한·쓰기 권한·공개 여부·댓글/첨부 옵션 선택
5. 생성 후 기본 필드와 목록·글쓰기 화면을 자동 준비
6. `필드 수정`, `첫 글 작성`, `홈페이지에 배치` 버튼 제시

### 5.2 필드 추가

1. 게시판의 `[필드 설정]` 진입
2. `[+ 필드 추가]` → 유형·라벨·안내 문구·필수 여부 지정
3. 선택형이면 옵션값과 표시 라벨 정의
4. 순서 조정, 폼 미리보기, 저장
5. 저장 성공 후 새 글쓰기·수정 화면에 반영

### 5.3 게시판 홈페이지 연결

v1.0 의 "섹션 추가 후 게시판 선택"은 코드형 템플릿과 FREE · BASIC 에서 쓸 수 없어 아래로 바꾼다.

- **기본 게시판(공지):** 템플릿의 `BOARD` 섹션과 자동으로 연결된다. 고객이 할 일은 없다. 삭제는 막고 비공개만 허용한다.
- **새 게시판 (T-140-B):** 생성 마법사 마지막 단계의 **[메뉴에 추가]**(기본 켬)로 `/{slug}/b/{게시판}` 이 메뉴에 들어간다. 슬러그는 자동으로 만들고 수정은 고급 설정에 둔다.
  - 메뉴 저장 키는 `board:{id}` — 주소를 바꿔도 이름 · 순서 · 숨김이 유지된다. 사용 안 함 · 휴지통이면 메뉴에서 빠지고 켜거나 복원하면 설정 그대로 돌아온다. 복제본은 메뉴에 넣지 않는다.
  - 주소를 바꾼 뒤 옛 주소는 404(자동 이동 없음, 화면이 경고). `/b/notice` 도 404 — 공지는 `/notice` 가 있어 중복 수집을 막는다.
  - 템플릿 샘플 미리보기에는 넣지 않고 내 콘텐츠 미리보기에서만 보인다.
  - 메뉴가 한 줄에 안 들어가면 넓은 화면에서도 헤더 토글로 접는다.
- **테마형 (T-141):** 주소 · 메뉴 저장 키는 코드형과 같다. 메뉴는 섹션 뒤에 게시판(순서 변경 없음), 게시판 화면에서 섹션 메뉴를 누르면 메인의 그 섹션으로 간다. 화면은 테마 CSS 변수로 6종이 함께 쓰고, 편집 툴바 · 템플릿 미리보기에는 넣지 않는다. 없는 주소는 미들웨어가 실제 404 로 끊는다.
- **메인 최신 글:** 지금은 공지만. 다른 게시판을 메인에 놓는 기능은 뒤에 검토한다.
- **템플릿을 바꿔도 글 · 주소 · 메뉴 설정은 그대로다 (AC-18).** 새 템플릿에 공지 페이지가 없으면 공지 글은 관리자 화면에만 남고, 목록에 "지금 템플릿에는 표시되지 않습니다"로 알린다.

### 5.4 게시판 삭제 및 복원

1. 삭제 전에 게시글 수와 연결된 페이지 목록 표시
2. 1차로 비활성화하거나 휴지통으로 이동
3. 공개 링크 처리 정책에 따라 안내 또는 404/410 반환
4. 관리자 휴지통에서 복원
5. **영구 삭제는 별도 관리자 권한·재확인·보관 정책 하에 수행**

## 6. 화면별 상세 설계

**코드형 목록 제목(T-163):** 추가 게시판은 상단 SubHero의 게시판 이름을 화면의 주 제목으로 사용한다. 목록형/갤러리/FAQ/카드 목록에서는 같은 이름의 제목을 `sr-only`로 시각적으로 숨기되 h2와 aria-labelledby 연결은 유지한다. 설명과 검색/분류/글쓰기/페이지 이동은 기존 위치에 남는다. 회원 전용 목록도 같은 표시를 쓴다. 기본 공지 목록과 테마형은 기존 제목을 표시한다. 로그인 안내·작성/상세 화면의 제목은 이번 범위에서 바꾸지 않는다.

### BM-01 게시판 목록 (`/admin/boards`) — 1단계는 기본 게시판만, 2단계 완성

| 영역 | 기능 |
|---|---|
| 상단 | 게시판 수, 게시판 추가 |
| 검색·필터 | 이름·유형·상태 검색 |
| 테이블 | 게시판명, URL, 유형, 게시글 수, 사용 상태, 수정일 |
| 행 액션 | 글 관리, 필드 설정, 기본 설정, 복제, 비활성화, 삭제 |
| 빈 화면 | 예제 게시판 만들기 안내 |
| 피드백 | 저장 성공/실패, 권한 없음, 요금제 초과 |

**UX:** 게시판 관리자는 생성·설정 중심, 게시글 운영자는 글 관리 중심 동선으로 분리한다.

**구현 (T-153):** 이름 부분 일치 검색(앞뒤 공백 · 영문 대소문자 무시), 4종 유형 · 사용 상태 필터를 함께 적용한다. 전체 · 결과 수, 검색 초기화, 결과 없음 안내를 제공한다. 조건은 `q` · `type` · `status` URL 쿼리로 보존한다. 알 수 없는 유형 · 상태는 전체로 취급한다. 기존 전체 목록 API 응답을 화면에서 필터링하며, 글쓰기 · 수정 바로가기는 검색 조건과 무관하게 원래 게시판을 찾는다.

**T-155 구현:** 목록에 기존 홈페이지 연결 화면과 같은 공유 도메인 기준 주소를 표시한다. 기본 공지는 `/{tenant_slug}/notice`, 새 게시판은 `/{tenant_slug}/b/{board_slug}`다. 사용 중인 게시판만 새 창으로 열며, 테마형 기본 공지와 템플릿 확인 전 기본 공지는 주소만 표시한다. 사용 안 함 게시판도 링크 없이 주소를 표시한다. 사업체 slug가 없으면 확인 불가를 안내한다. 글 관리 링크와 홈페이지 링크는 별개다. `설정 수정`은 관리자 게시판 응답(목록 · 생성 · 수정 · 복원)에 추가한 기존 DB의 `updated_at`을 브라우저 시간대로 표시하며, 글의 최근 수정일 집계가 아니다. 날짜를 확인할 수 없을 때 현재 시각으로 대신하지 않는다.

**T-156 구현:** 목록의 각 행에서 설정 · 칸만 복제한 뒤 복사본 설정 화면으로 이동하거나, 확인 후 게시판을 휴지통으로 옮길 수 있다. 확인창은 게시판 이름 · 글 수 · 홈페이지 메뉴와 주소에 미치는 영향을 알린다. 삭제 후 검색 조건을 유지하고 목록 · 글 수 · 한도 · 메뉴를 기존 쿼리 무효화로 갱신한다. 보기 전용에는 작업 버튼을 두지 않고 기본 게시판에는 삭제 버튼을 두지 않는다(복제는 가능). 한도 확인 전 · 실패 · 초과 시 복제를 막고 서버도 기존 한도를 검사한다. 복제/삭제 처리 중에는 모든 행의 두 작업을 잠그며, 실패하면 원본 목록을 유지하고 이유를 안내한다. 영구 삭제가 아니며 서버 API · 보호 규칙은 바꾸지 않는다.

**T-157 구현:** 목록에 추가 게시판(기본 게시판이 아닌 것)이 없으면 기본 공지 유무와 관계없이 소식(목록형) · 사진 모음(갤러리형) · 자주 묻는 질문(FAQ형) · 채용 안내(카드형) 예시를 안내한다. 기존 추가 게시판이 있으면 검색 결과가 없어도 이 안내는 내지 않는다. 생성 권한과 한도가 확인된 경우에만 `/admin/boards/new?example={ID}`로 연결한다. 허용된 ID만 이름 · 설명 · 유형의 초기값으로 쓰며, 사용자가 기존 3단계 생성 화면에서 바꾸고 검토한 뒤 만들기를 눌러 저장한다. 알 수 없는 ID와 임의 이름/유형 쿼리는 무시한다. 안내를 보거나 예시를 고르는 것만으로 생성 요청을 보내지 않는다. 예제 글 · 추가 칸을 자동으로 만들지 않으며, 유형별 기본 필드와 업종별 프리셋은 별도 후속이다.

### BM-02 게시판 생성 마법사 (`/admin/boards/new`) — 2단계

| 단계 | 필드 | 검증 |
|---|---|---|
| 1. 기본 정보 | 이름, 설명, 슬러그(고급 설정 — 비우면 `board-1` 처럼 자동) | 필수·길이·중복·예약어 |
| 2. 유형 | 게시판 타입, 기본 스키마 | 타입별 기본 필드 로딩 — 후속 (TASK 후속 후보, T-152 대조에서 확인) |
| 3. 운영 설정 | 사용 여부 (T-140-A). 읽기·쓰기 권한, 댓글·첨부는 후속 | 잘못된 권한 조합 방지 |

**후속 동작:** 생성 완료 화면에서 `첫 글 쓰기` / `칸 설정` / `게시판 설정`으로 이동 (T-144). `사이트에 배치` 버튼은 두지 않는다 — 마법사의 "홈페이지 상단 메뉴에 추가"가 그 일을 한다.

### BM-03 게시판 설정 (`/admin/boards/:boardId/settings`) — 2단계

- 기본: 이름, 설명, URL, 게시판 유형(게시글 발생 이후 타입 변경 정책 검토)
- 노출: 활성 상태, 기본 정렬, 페이지당 글 수, 목록 컬럼
- 운영: 댓글·비밀글·첨부 파일·상단 고정 사용 여부
- 권한: 열람·작성·수정·삭제·댓글·다운로드 사용자 범주
- SEO: 게시판 제목, 설명, 검색엔진 노출 여부
- 위험 작업: 비활성화, 복제, 휴지통 이동

**목록 표시 · 검색 노출 (T-146):** 검색 노출은 `기본 정보` 탭, 정렬 · 글 수는 `게시판 디자인` 탭에서 고른다 (T-148). 값은 `boards.settings` (DB 구조 변경 없음).
- 기본 정렬: 최신순(기본) · 오래된순 · 제목순. 상단 고정 글은 언제나 먼저. 메인 최신 공지는 설정과 관계없이 최신순, 글 화면의 이전 · 다음 글은 공개일 순서 그대로
- 페이지당 글 수: 자동(목록 10 · 갤러리 12 · FAQ 20) · 10 · 20 · 30
- 검색 제목(60자) · 검색 설명(160자) · 검색 결과에 표시: 새 게시판만. 제목 · 설명은 목록 화면에, 노출을 끄면 목록 · 글 화면 모두 noindex 이고 사이트맵에서 빠진다. 주소로는 열린다. 공지는 화면이 템플릿 페이지라 정렬 · 글 수만 쓴다. 소셜 공유 문구(OG)는 사이트 SEO 설정 그대로

**목록 표시 필드 (T-159):** 새 게시판의 디자인 탭에 `목록에 표시할 추가 정보`를 둔다(목록형/카드형 T-159, 갤러리/FAQ T-160). 기존 `show_in_list`를 필드마다 바꾸는 즉시 저장하며, 디자인 폼의 저장 버튼과 독립이다(D-13 유지). 저장 중에는 다른 필드 변경도 잠그고, 실패하면 선택을 유지하며 오류를 안내한다. 조회 실패는 다시 시도할 수 있고 보기 전용은 변경할 수 없다. 홈페이지 비표시 칸은 관리자에서만 보인다는 안내와 함께 선택할 수 있다. 칸 이름 · 순서 · 홈페이지 표시는 필드 관리에서 고친다. 기본 게시판에는 제공하지 않는다. 작성일은 기존 디자인 설정대로 고른다.

공개 목록형은 `list_fields`를 제목 아래에 표시한다(코드형 · 테마형 공통). 홈페이지 표시와 목록 표시를 모두 켠, 삭제 안 한 칸의 빈 값 아닌 항목만 순서대로 내보낸다. 선택지는 이름, 0 · 아니오도 표시하며 사진은 ‘사진 있음’, URL은 글자로 보여 준다. 비밀글은 칸을 내보내지 않는다. 카드형은 기존 `card_fields`를 유지한다. 갤러리도 제목 아래에, FAQ는 펼치기 전에도 질문 아래에 `list_fields`를 표시한다(T-160). 사진/링크는 글자이며 긴 값은 줄바꿈한다. 비밀글 필드는 서버와 화면에서 제외한다. 임의의 독립 표 열 · 너비/순서는 후속이다.

### BM-04 필드 빌더 (`/admin/boards/:boardId/fields`) — 4단계

```text
고객 후기 > 필드 빌더                      [미리보기] [변경 저장]
┌─────────────────────────────────────────────────────┐
```

**T-142-B-2 구현:** 공개 글 상세에 칸을 제목 아래 · 본문 위에 "이름: 값"으로 보여 준다 (코드형 · 테마형). 숨긴 칸 · 삭제한 칸 · 빈 칸은 나가지 않고, 선택지는 내부 값이 아닌 이름으로, 별점은 ★, 참/거짓은 예/아니오, 사진은 이미지, 글자는 HTML 로 해석하지 않는다. 공개 글 목록에는 표시하지 않는다 (유형 · 템플릿마다 자리가 달라 후속). 로그인한 관리자에게는 글 상세에 [수정]이 보이고, 공개 뒤 글 목록에 "홈페이지에서 보기"가 나온다.

**T-142-B-1 구현:** 저장은 칸마다 바로 — 시안의 [변경 저장] 버튼은 두지 않는다 (API 가 칸 단위고, 일부만 저장되는 상태를 막는다). 순서는 끌기와 위 · 아래 버튼. 값이 있는 칸은 유형을 잠그고 글 수를 보여 주며, 삭제 전에 영향받는 글 수를 알린다. 글쓰기 폼은 제목 → 칸 → 내용 순서이고, 필수 규칙(8.4)을 서버와 같게 미리 검사한다. 고객에게 안 보이는 선택지 내부 값은 `opt_1` 처럼 자동이라 이름을 바꿔도 값이 유지된다.

**T-142-A 결정:** 기본 게시판(공지)에는 칸을 추가하지 않는다 — 화면이 고정이고 FREE · BASIC 도 자연히 제외된다. 게시판당 20개. `field_key` 는 비우면 `field_1` 처럼 자동이고 지운 이름은 재사용하지 않는다. 시스템 이름(`title` · `body` · `status` 등)은 쓸 수 없다 (D-07). 이미지는 본문과 같은 주소 검사, 칸당 한 장 — 8.3 의 미디어 자산 ID 는 채택하지 않았다.

**설계 주의:** 기본 제목·본문 등 시스템 필드와 사용자 정의 필드는 구분한다. 모든 유형의 게시판에 작성자 필드를 무조건 공개하거나 수정 가능하게 두지 않는다. 업종·유형별 기본값을 다르게 적용한다.

### BM-05 게시글 통합 목록 (`/admin/posts`) — 2단계 (1단계는 게시판별 목록)

- 검색: 제목·내용·작성자(권한·개인정보 정책 고려)
- 필터: 게시판, 카테고리, 작성/수정일, 상태
- 열: 체크박스, 제목, 게시판, 상태, 작성일, 수정일, 액션
- 일괄: 공개/비공개, 휴지통은 2단계, 다른 게시판으로 이동(필드 호환성 검사)은 4단계 뒤

**T-158 구현:** 전체 글과 글 휴지통에도 각 게시판의 `글 목록에 표시`를 켠 칸 값을 제목 아래에 표시한다. 기존 관리자 API의 `custom_data`와 게시판별 필드 정의를 사용하며, 같은 게시판의 행은 조회 캐시를 공유한다. 값이 없는 행은 필드 조회를 생략한다. 표시 해제 · 삭제 · 정의 없는 칸과 빈 값은 제외하고, 0 · 아니오는 표시한다. 선택지는 이름, 사진은 ‘사진 있음’으로 보여 준다. `홈페이지에 표시`를 끈 칸도 관리자에서는 기존 게시판별 목록과 동일하게 볼 수 있다. 필드 정보를 기다리거나 읽지 못한 경우 안내하며 실패 시 다시 시도할 수 있다. 원시 키/값을 대신 노출하지 않는다. 목록형 공개 표시와 디자인 탭의 필드 선택은 T-159에서 연결했다. 독립 표 열 설정은 후속이다.

**T-161 구현:** 전체 글에서 작성일 시작/종료 날짜와 제목 검색을 함께 적용한다. 작성일은 `created_at`(최초 저장 시각)이며 공개일/수정일과 다르다. 브라우저 시간대의 시작일 자정 이상, 종료일 다음 날 자정 미만으로 바꾸어 UTC 시각을 보낸다. 종료일을 포함하고, 24시간 덧셈 대신 다음 달력 날짜를 사용해 서머타임도 처리한다. 한쪽 날짜만 정할 수 있다. 잘못된 날짜나 역전된 기간은 요청을 보내지 않고 안내한다. 기간 초기화는 다른 적용 조건을 유지한다. 날짜는 검색 전까지 적용하지 않는다. 기간 적용/초기화 시 페이지와 글 선택을 비운다. 게시판/분류/상태/휴지통 조건과 함께 적용하고, API의 목록과 total은 같은 조건으로 조회한다. 보기 전용도 조회 가능하다.

**T-154 구현:** 전체 글에서 게시판을 선택한 뒤 해당 게시판의 카테고리로 좁혀 본다. 기본 게시판과 분류가 없는 게시판은 선택을 끈다. 숨긴 카테고리도 관리자가 선택할 수 있고 `(숨김)`으로 표시한다. 카테고리 로딩 · 실패 · 없음은 구분하고 실패 시 다시 시도할 수 있다. 게시판을 바꾸거나 전체로 돌아가면 카테고리 조건을 비우며, 조건 변경 시 페이지와 글 선택도 초기화한다. 새 조건의 결과를 기다리는 동안 이전 목록의 글 선택은 비활성화한다. 제목 · 상태 · 휴지통 조건과 함께 적용한다.

**T-140-C 구현:** 게시판 · 상태 · 제목 검색 · 휴지통 보기, 일괄 공개 · 비공개 · 휴지통 · 복원. 선택은 지금 페이지 안에서, 한 번에 100개까지. 처리할 수 없는 글이 섞이면 전부 취소한다. 내용 · 작성자 검색과 수정일/공개일 필터는 후속. 작성일 필터는 T-161에서 구현했다. 일괄 공개도 낱개와 같이 공개일을 정하고 공지면 샘플을 비운다.
- 페이지네이션·정렬·최신 데이터 갱신
- 게시판마다 다른 사용자 필드를 목록 컬럼에 선택 노출

### BM-09 카테고리 (`/admin/boards/:boardId/categories`) — T-149

기획안 v2.2 의 BRD-005 중 1단계 분류만. 2단계(상위 · 하위) · 여러 원본 일괄 합치기 · 코드는 후속. 분류 검색은 T-164에서 구현했다. 단일 카테고리 합치기 명시 동선은 T-162에서 기존 삭제/이동 API로 연결했다.

- 검색(T-164): 카테고리 이름 부분 일치(앞뒤 공백 · 대소문자 무시)와 홈페이지 표시/숨김 상태를 함께 적용한다. 기존 전체 목록을 화면에서 즉시 필터링하고 전체/결과 수 · 검색 초기화를 제공한다. 검색 결과 없음과 분류 자체가 없는 상태는 구분한다. 검색 중에는 드래그 · 키보드 · 위아래 순서 변경을 잠그고 초기화하면 전체 순서 변경을 다시 제공한다. 이름 변경 · 표시/숨김 · 합치기 · 삭제는 유지한다. 합치기/삭제 이동 대상과 생성 한도는 필터 전 전체 분류를 기준으로 한다. 저장 뒤 조회 갱신에도 조건을 유지해 결과를 다시 걸러 주며, 다른 게시판으로 이동하면 초기화한다. 보기 전용도 검색할 수 있다. 검색 조건을 URL에 저장하지 않는다.
- 추가 · 이름 바꾸기 · 홈페이지에서 숨기기 · 순서(끌기 · 위아래) · 삭제. 게시판당 30개, 이름은 30자이고 게시판 안에서 겹치지 않는다
- 기본 게시판(공지)은 화면이 템플릿 페이지라 탭이 없고 API 도 막는다 (필드와 같음)
- 삭제: 그 분류에 글이 있으면 옮길 곳(다른 분류 · 분류 없음)을 고른다. 휴지통 글도 함께 옮긴다. 분류는 소프트 삭제이고 같은 이름을 다시 쓸 수 있다
- 합치기(T-162): 행의 합치기 버튼에서 같은 게시판의 다른 카테고리를 필수로 고르고 원본/대상을 확인한다. 대상이 없으면 버튼을 끄고 뷰어에게는 숨긴다. 일반 글 수가 0인 원본도 휴지통 글을 이동할 수 있다. 원본 카테고리는 소프트 삭제되며 글 내용/공개 상태는 유지된다. 숨김 대상은 홈페이지 탭에서 숨겨져 있다는 영향을 안내한다. 기존 DELETE의 move_to만 사용한다. 처리 중 닫기/대상 변경/중복 실행을 막고, 실패 시 선택과 목록을 유지해 재시도할 수 있다. 성공하면 해당 게시판의 카테고리/글 쿼리와 전체 글 쿼리를 무효화한다. 기존 삭제에도 같은 조회 갱신을 적용한다. 전체 글에서 성공적으로 다시 읽은 분류 목록에 현재 필터가 없으면 그 조건을 해제하고 페이지/선택을 초기화한다. 나머지 조회 조건은 유지한다.
- 숨긴 분류는 홈페이지 탭에서만 빠지고 글은 `전체` 에 그대로 보인다. 글쓰기에서는 `(숨김)` 을 붙여 고를 수 있다
- 글쓰기 · 수정: 분류가 있는 게시판에만 `카테고리` 칸. 글 관리 목록: 분류 이름 표시 · 분류로 걸러 보기
- 홈페이지: 분류가 있으면 목록 위에 `전체` + 분류 탭. 주소는 `?c={분류 id}` 이고 검색 · 페이지 이동에 유지된다. 없는 · 숨긴 분류 주소는 `전체` 로 보여 준다. 코드형(hospital-a) · 테마형 모두
- 게시판 복제 때 분류도 복제한다 (글은 복제하지 않으니 이름 · 순서 · 숨김만)
- 표 `board_categories`, 글의 `board_posts.category_id` (마이그레이션 0042). 다른 게시판 · 지운 분류는 글에 붙일 수 없다

### BM-10 권한 (`/admin/boards/:boardId/permissions`) — T-150

기획안 v2.2 의 BRD-006 을 지금 역할(관리자 · 보기 전용 · 방문자 회원 · 방문자)에 맞춘 범위. 편집자 역할 · 승인 · 권한 테스트는 후속.

- **글 읽기 (T-150-A):** `누구나`(기본) · `회원만`. 값은 `boards.settings.permissions.read` — 표 변경 없음
- **서버가 강제한다:** `회원만` 게시판의 공개 글 목록 · 상세 API 는 그 사업체의 로그인한 방문자 회원 토큰만 받는다. 토큰 없음 · 만료 · 탈퇴 · 비밀번호 변경 전 토큰은 401, 관리자 토큰 · 다른 사업체 회원 토큰 · 회원 기능을 끈 사업체는 403. 응답은 `Cache-Control: private, no-store`
- **공개 캐시에 남기지 않는다:** 홈페이지 서버는 이 게시판의 글을 읽지 않는다. 화면이 로그인을 확인하고 브라우저에서 회원 토큰으로 읽는다. 로그인하지 않았으면 `회원만 볼 수 있는 게시판입니다` 와 [로그인](돌아올 주소 포함)
- **검색 제외:** 목록 · 상세 페이지 `noindex`, 사이트맵에서 게시판과 글 모두 제외(백엔드 · 홈페이지 양쪽)
- 상단 메뉴에는 그대로 보인다. 공개 사이트 응답의 `boards[].read_access` 로 화면이 구분한다
- 방문자 회원 기능(`SITE_MEMBER`)이 꺼진 사업체는 `회원만` 을 고를 수 없다(409). 이미 `회원만` 인데 기능을 끄면 아무도 읽을 수 없고, 관리자 화면에 경고가 나온다
- 기본 게시판(공지)은 화면이 템플릿 페이지라 권한 · 운영 설정 탭이 없고, 서버도 권한 · 운영 설정 변경과 비밀글을 막는다(409, 기본값 저장은 허용, T-152)
- 바꾸면 `BOARD_UPDATED` 감사 로그에 이전 · 이후 권한이 남는다
- **글쓰기 (T-150-B):** `관리자만`(기본) · `회원도`. `회원도` 면 홈페이지 목록에 [글쓰기], 주소 `/b/{게시판}/write` · `/b/{게시판}/{글}/edit` (검색 제외)
  - 폼은 제목 · 내용(글자만) · 카테고리. 서버가 글자를 문단 노드로 만든다 — 서식 · 링크 · 사진 · 추가 칸 없음. 글은 바로 공개되고 `board_posts.author_member_id` 에 작성 회원이 남는다 (마이그레이션 0043)
  - 자기 글만 고치고 지운다. 남의 글 · 관리자 글 · 휴지통 글은 404. 글쓰기를 꺼도 자기 글 삭제는 된다(고치기는 안 됨). 삭제는 휴지통으로
  - 회원 한 명당 1시간 10개 (429). 관리자 글 관리 · 전체 글에 `회원 작성 · 이름`, 관리자는 비공개 · 삭제할 수 있다
  - **켤 수 없는 경우 (409, 화면에 이유):** 병원 업종(`HOSPITAL`, D-14), 회원 기능 꺼짐, 필수 칸이 있는 게시판. 켠 뒤에는 필수 칸을 만들 수 없다. 업종을 병원으로 바꾸면 이미 켠 게시판도 서버가 글쓰기를 막는다(403)
  - 관리자 화면은 `GET /boards/{id}/permission-options` 로 고를 수 없는 이유를 받는다

### BM-11 운영 설정 (`/admin/boards/:boardId/operation`) — T-151

기획안 v2.2 의 BRD-007 중 회원 글쓰기에 필요한 것부터. 댓글 · 첨부 · 파일 크기 등은 후속.

- **비밀글 허용 (T-151-A):** 켜면 회원 글쓰기 폼에 `비밀글로 등록`. 관리자 글쓰기에도 `비밀글` 토글(허용했거나 이미 비밀글일 때). 값은 `boards.settings.operation.allow_secret`, 글은 `board_posts.is_secret` (마이그레이션 0044)
  - 공개 목록: 제목과 자물쇠만 — 요약 · 사진 · FAQ 답변 · 카드 칸은 서버가 내보내지 않는다
  - 공개 상세: 쓴 회원의 토큰이 아니면 `locked: true` 와 제목만(본문 · 칸 없음). 쓴 회원에게는 내용을 주고 `Cache-Control: private, no-store`. 홈페이지 서버는 잠긴 글만 받고, 쓴 회원이면 브라우저가 다시 읽는다
  - 사이트맵 제외. 관리자는 관리자 화면에서 늘 내용을 본다
  - 허용을 꺼도 이미 쓴 비밀글은 비밀로 남는다. 그 글은 고칠 때 비밀을 풀 수는 있지만 새로 비밀로 바꿀 수는 없다(409)
- **새 글 알림 (T-151-A):** 켜면 회원이 새 글을 쓸 때 관리자 화면에 실시간 알림(문의 알림과 같은 SSE 채널, 종류 `new_post`). 제목 · 게시판 이름만 보낸다. 알림이 실패해도 글은 저장된다. 고친 글은 알리지 않는다
- **비회원 글쓰기 (T-151-B):** `operation.allow_guest`. 글쓰기 `회원도` 이고 글 읽기가 `누구나` 인 게시판에서만 열린다. 병원 업종 · 필수 칸이 있는 게시판은 켤 수 없다(409, 회원 글쓰기와 같은 이유). 업종을 병원으로 바꾸면 서버가 막는다(403)
  - 폼: 이름(20자) · 글 비밀번호(4~50자) · 제목 · 내용 · 카테고리 · 비밀글 · 개인정보 수집 · 이용 동의(필수). reCAPTCHA v3(이 폼의 action 토큰만, Google 장애는 503 안내 — T-152), 같은 IP 1시간 5개(Redis, 장애 시 허용)
  - 글 비밀번호는 bcrypt 해시로만 `board_posts.guest_password_hash`, 이름은 `guest_name` (마이그레이션 0045). IP 는 저장하지 않는다
  - 고치기 · 지우기 · 비밀글 열기는 글 비밀번호로. 틀린 비밀번호는 사업체 안에서 같은 IP 10분 5번까지(여러 글을 돌아가며 시도해도 함께 센다, T-152), 넘으면 맞아도 429. Redis 를 못 쓰면 거절(맞히기 차단 우선). 회원 글 · 관리자 글은 비밀번호로 열 수 없다(404). 응답 캐시 금지
  - D-08 (비회원 게시글 수정 · 삭제 방식) → 글 비밀번호로 결정
- **신고 (T-151-B):** 공개 글 상세에 [신고] — 스팸 · 광고 / 욕설 · 비방 / 개인정보 노출 / 기타 + 설명(200자). 같은 사람(회원 id 또는 IP 를 서버 비밀값으로 해시)은 한 글에 한 번(409). IP 해시별 1시간 10번. 처리하지 않은 신고가 3건이면 글을 자동 비공개
  - 관리자 `신고된 글` — 신고 수 · 사유 · 설명, [신고 닫기] [다시 공개] [비공개로] [휴지통으로]. 처리하면 그 글의 신고가 닫히고 감사 로그 `POST_REPORTS_*`
  - 표 `board_post_reports` (RLS, 원래 IP · 회원 id 는 남기지 않는다)

## 7. 게시판 유형과 템플릿

| 유형 | 기본 UI | 대표 기본 필드 | 특화 기능 |
|---|---|---|---|
| 일반 목록 | 테이블 | 제목, 본문, 작성일 | 공지 고정, 검색, 정렬 |
| 갤러리 | 카드 그리드 | 제목, 요약, 대표 이미지 | 썸네일, 라이트박스 |
| 웹진 | 이미지+요약 리스트 | 제목, 본문, 썸네일, 태그 | 분류, 공유, 읽기 시간(P1) |

| 1:1 문의 | 본인 전용 목록 | 제목, 문의 내용, 연락 수단 | 본인 인증·알림·상담원 배정 |

**카드형을 T-148 에서 더했다** (채용공고 · 프로젝트 · 제품 소개, 페이지당 12개). 다음은 2단계 때 기록:

**2단계에서 만드는 유형은 일반 목록 · 갤러리 · FAQ 3개다.** 유형 수에 템플릿 수를 곱한 만큼 화면이 늘어나기 때문이다. 페이지당 목록 10개 · 갤러리 12개(썸네일은 본문의 첫 사진, 없으면 빈 칸) · FAQ 20개(펼침, 글 주소도 유지). 라이트박스는 아직 없다. Q&A 는 온라인 상담과 겹쳐 P1, 웹진 · 1:1 은 P2.

**정책:** 기존 `inquiries` 기반의 상담/예약은 초기에는 위 범용 Q&A와 혼합하지 않고 UI·API 호환 계층으로 제공한다.

### 업종별 게시판 프리셋 — P2

- 병원: 공지사항, 의료진 소개, 병원 소식 — **고객 후기 제외.** 의료법 제56조의 치료경험담 광고 금지에 걸릴 수 있어, 전문가 확인 전에는 넣지 않는다
- 펜션: 객실 소개, 이용 안내, 후기, 주변 명소
- 스타트업/웹에이전시: 포트폴리오, 뉴스, 채용 공고, FAQ
- 프리셋은 **초기 필드와 표시 형태**를 제공하고, 고객이 자유롭게 수정할 수 있게 한다.

## 8. 데이터 모델 제안

### 8.1 원칙

- PostgreSQL의 공통 게시글 컬럼 + `custom_data JSONB` 사용.
- 커스텀 필드 정의는 별도 `board_fields` 테이블로 관리.
- 게시글마다 임의의 실제 SQL 컬럼을 추가하지 않는다.
- 구조화된 공통 속성(제목·상태·작성자·일시)은 일반 컬럼으로 유지.
- 모든 테넌트 소유 테이블에 `tenant_id` 포함 및 RLS 적용.
- 복합 FK·유니크 제약, 삭제 정책 및 인덱스는 실제 마이그레이션에서 구체화.

### 8.2 테이블 목록

| 테이블 | 주요 컬럼/기능 |
|---|---|
| `boards` | `id`, `tenant_id`, `name`, `slug`, `type`, `status`, `system_key`(기본 게시판 — 삭제 보호), `settings`, `deleted_at` |
| `board_fields` (4단계) | `id`, `tenant_id`, `board_id`, `field_key`, `label`, `field_type`, `field_options`, `is_required`, `display_order`, `deleted_at` |
| `board_posts` | `id`, `tenant_id`, `board_id`, `title`, `body`(노드 JSONB), `status`, `is_pinned`, `custom_data`, `author_id`, `published_at`, `deleted_at` |
| `board_categories` (T-149) | `id`, `tenant_id`, `board_id`, `name`, `is_active`, `display_order`, `deleted_at` — 이름은 지우지 않은 것 중 게시판 안에서 하나. 글은 `board_posts.category_id` |
| `board_permissions` | 역할·행위별 읽기/쓰기/관리 정책 |
| `post_files` | 게시글별 스토리지 객체 메타, 접근 레벨 |
| `post_comments` | 댓글·대댓글, 상태 (P1) |
| `post_revisions` | 게시글 이전 버전, 복원 (P1) |

**두지 않는 표:** `board_audit_logs` — 기존 `audit_logs` 에 `tenant_id` 를 더해 쓴다 (T-140-C 구현, 11.4). 1단계는 `author_id` · `updated_at` · `deleted_at` 으로 충분하다.

**본문 형식 (결정, T-143 에서 변경 — D-11):** HTML 이 아닌 Tiptap 노드 JSON. 서버가 허용 목록(`schemas/rich_body.py`)으로 다시 만들어 위험한 링크 · 사진 주소를 거부하고 모르는 속성을 버린다. 이전 형식 `[{type: 'p', text} | {type: 'ul', items} | {type: 'image', src, alt}]` 도 기존 글 · 샘플을 위해 읽고 받으며, 고쳐 저장하면 새 형식이 된다.

### 8.3 JSONB 데이터 예시

```json
{
  "id": "post_uuid",
  "tenant_id": "tenant_uuid",
  "board_id": "board_uuid",
  "title": "친절한 서비스 후기",
  "status": "published",
  "custom_data": {
    "rating": 5,
    "visit_date": "2026-11-04",
    "review_images": ["media_asset_uuid"]
  }
}
```

이미지 주소 원문을 JSONB에 고정하기보다 미디어 자산 ID로 참조하는 방식은 **신규 제안**이다. 기존 저장 방식과의 호환 여부 확인 필요.

### 8.4 필드 변경 안정성

| 변경 | 처리 정책 |
|---|---|
| 라벨/도움말/순서 | 즉시 변경 가능 |
| 새 필드 추가 | 기존 글은 값 미존재(`null` 또는 기본값 처리) |
| 선택 옵션 수정 | 기존 값이 쓰이는 경우 경고·매핑 제공 |
| 필수 옵션 변경 | 기존 글의 누락값과 새 글 입력을 구분하여 검증 |
| 필드 삭제 | 소프트 삭제, 데이터 유지, 관리자 복원 제공 |
| 필드 키 변경 | 허용하지 않음 |
| 필드 타입 변경 | 값 존재 시 원칙적으로 차단; 데이터 마이그레이션 도구는 후속 검토 |

**T-142-A 구현:** 필수 칸은 공개할 때만 검사한다 — 임시저장 · 비공개는 통과. 한 번도 공개한 적 없는 글은 전부 검사하고, 공개했던 글은 있던 값을 비우는 것만 막는다 (일괄 공개도 같음). 쓰고 있는 선택지 삭제는 409, 이름 변경은 허용, 매핑 도구는 후속. 타입 변경 · 선택지 사용 검사에는 휴지통 글도 센다. 글을 고칠 때 보낸 칸만 바뀌고, 삭제한 칸은 새 값을 받지 않되 있던 값은 그대로 둔다. 기본값은 글을 새로 만들 때만 채운다.

### 8.5 인덱스·성능

- 기본: `(tenant_id, board_id, status, published_at DESC)` 중심 조회 인덱스 검토.
- `boards`의 테넌트별 슬러그 중복 방지 및 휴지통 정책 고려.
- 검색이 잦은 JSONB 필드만 개별 표현식/GIN 인덱스를 선택적으로 적용.
- 목록·검색은 서버 페이지네이션 사용; 대량 데이터의 전체 조회 금지.
- 공개 페이지의 캐시 무효화 기준을 게시글 발행·수정·삭제 이벤트와 연결.

### 9.2 공개 API

v1.0 의 `/api/public/boards/{board_slug}` 는 슬러그가 테넌트별이라 어느 사업체인지 알 수 없어, 기존 `/api/public/site/{tenant_slug}` 아래로 옮긴다.

| Method | Path | 기능 | 단계 |
|---|---|---|---|
| GET | `/api/public/site/{tenant_slug}/boards/{board_slug}/posts` | 공개 글 목록 (`?q=` · `?page=` · `?size=` · `?category=` · `?order=latest`, 고정 글 먼저). `회원만` 게시판은 방문자 회원 토큰 필요 (T-150) | 1 |
| GET | `/api/public/site/{tenant_slug}/boards/{board_slug}/posts/{post_id}` | 글 상세 + 이전 · 다음 글 + 표시할 칸 `fields` | 1 · 4 |
| POST | `/api/public/site/{tenant_slug}/boards/{board_slug}/posts` | 회원 글쓰기 (`title` · `content` 글자 · `category_id`, 방문자 회원 토큰) — T-150-B | P1 |
| GET | `/api/public/site/{tenant_slug}/boards/{board_slug}/posts/{post_id}/mine` | 내가 쓴 글이면 고치기 값, 아니면 404 — T-150-B | P1 |
| PATCH · DELETE | `/api/public/site/{tenant_slug}/boards/{board_slug}/posts/{post_id}` | 자기 글 고치기 · 휴지통 — T-150-B | P1 |
| POST | `/api/public/site/{tenant_slug}/boards/{board_slug}/posts/guest` | 비회원 글쓰기 (이름 · 글 비밀번호 · 동의 · reCAPTCHA) — T-151-B | P1 |
| POST · PATCH | `.../posts/{post_id}/guest/verify` · `.../posts/{post_id}/guest` · `.../guest/delete` | 글 비밀번호로 열기 · 고치기 · 휴지통 — T-151-B | P1 |
| POST | `/api/public/site/{tenant_slug}/boards/{board_slug}/posts/{post_id}/report` | 글 신고 — T-151-B | P1 |
| GET | `/api/public/site/{tenant_slug}` 의 `boards` | 사용 중인 새 게시판 (이름 · 슬러그 · 설명 · 유형 · 분류 `categories` · `read_access` · `write_access` · `allow_secret` · `allow_guest`) — `write_access` · `allow_guest` 는 저장값이 아니라 지금 실제로 열리는지(병원 업종 · 회원 기능 · 회원만 읽기 반영, T-152) | 2 |
| GET | `/api/public/site/{tenant_slug}/boards/{board_slug}` | 공개 게시판 정보와 허용된 필드 — 필드가 생기는 4단계에서 필요하면 | 4 |

목록 응답의 `list_fields`는 목록형 · 갤러리 · FAQ 표시용 `{key, label, field_type, value}` 배열이다(T-159). 홈페이지/목록 표시를 모두 켠 칸만 포함하고 비밀글과 카드형은 null이다. 카드형은 기존 `card_fields`를 사용한다. `custom_data`는 공개하지 않는다.

- 글 목록 항목에는 `thumbnail`(본문의 첫 사진)이 있고, FAQ 게시판만 `body` 까지 준다.
- `GET /api/public/site/{tenant_slug}/sitemap-posts` — 사이트맵용 공개 글 (최근 수정 순, 최대 5,000개, T-140-C).
- 공개 API 는 `PUBLISHED` 이고 삭제되지 않은 글만 돌려준다. 비활성 사업체는 404.
- 공개 API도 **도메인/테넌트 식별, 회원 인증, 접근 권한, 비공개 글 보호, 요청 빈도 제한**을 거쳐야 한다.
- 다른 테넌트의 글 id 로 조회하면 404 다.
- 기존 상담 API는 그대로 둔다.

### 9.3 응답·에러

- 기존 CMS의 `{ success, data, meta }` 응답 규격 및 공통 에러 응답을 유지한다.
- 필드별 유효성 오류는 `field` 및 `details`로 반환해 화면에서 위치별 안내한다.
- 중복 슬러그, 권한 부족, 타입 오류, 플랜 제한, 데이터 충돌을 개별 코드로 관리한다.

## 11. 보안·운영 정책

### 11.1 접근 제어

- 테넌트 관리자와 콘텐츠 운영자의 권한을 분리한다.
- **게시판별·동작별** 읽기/쓰기/수정/삭제/댓글/다운로드 권한을 검사한다.
- 비밀글·1:1 게시판은 **목록뿐 아니라 상세·검색·파일·캐시** 단계에서도 차단한다.
- 회원만 읽는 게시판(T-150-A)은 공개 API 에서 회원 토큰을 검사하고, 홈페이지 서버 캐시 · 사이트맵 · 검색에 글을 넣지 않는다 (BM-10).
- RLS는 최후 방어선이며 FastAPI의 리소스 수준 검증을 대체하지 않는다.

### 11.2 입력·파일 보안

- 허용 필드만 저장(서버에서 정의되지 않은 `custom_data` 키 거부).
- 에디터 HTML은 XSS를 고려해 정화하거나 안전한 구조화 포맷으로 저장.
- 업로드 파일의 MIME/확장자/용량/서명 검증, 악성 파일 대응, 스토리지 접근 제어. **지금 버킷은 익명 읽기 공개라 비공개 글의 파일을 막을 수 없다** — 비공개 파일은 별도 버킷과 서명 URL 을 만들기 전에는 받지 않는다 (P1).
- 외부 URL 필드는 `javascript:` 등 위험 스킴 차단.
- 공개 글쓰기·비밀번호 해제는 현행 CMS의 reCAPTCHA/요청 제한 정책과 정합성 유지.

### 11.3 법률 확인 (방문자 글쓰기를 열기 전 — P1)

- 병원 후기는 의료법 제56조 치료경험담 광고 금지에 해당할 수 있다.
- 방문자 글에는 개인정보 수집 고지(상위 기획서 10.2 #7과 함께), 권리 침해 신고 · 게시 중단 절차가 필요하다.
- 전문가 확인 전의 메모이며 확정된 법률 해석이 아니다.

### 11.4 감사·복구

- 생성·필드 변경·권한 변경·글 강제 삭제·복원을 감사 로그에 기록.
- 삭제 시 실제 파일 보존 및 정리 정책을 설정한다. 해지 고객 데이터 파기(상위 기획서 10.2 #5)가 정해지면 새 표도 포함한다.
- 게시글/게시판 복원 시 이름·슬러그 충돌 처리와 참조 무결성을 확인한다.
- 이력 로그에는 불필요한 민감한 본문이나 비밀번호를 저장하지 않는다.
- **T-140-C 구현:** `audit_logs.tenant_id` + RLS(읽기는 자기 사업체 · 슈퍼 어드민, 수정 · 삭제는 슈퍼 어드민만, 쓰기는 비운 값 허용 — 로그인 전 요청). 기록: `BOARD_CREATED` · `UPDATED` · `DUPLICATED` · `DELETED` · `RESTORED`, `POST_DELETED` · `RESTORED`, `POST_BULK_*`. 값은 게시판 이름 · 슬러그 · 유형 · 상태, 글 제목 · 상태 · id 만. 일반 글 저장은 남기지 않는다. 이후 추가: `BOARD_FIELD_*` (T-142-A), `BOARD_CATEGORY_*` (T-149), 권한 · 운영 설정 변경은 `BOARD_UPDATED` 의 이전 · 이후 값 (T-150 · T-151), 신고 처리 `POST_REPORTS_*` (T-151-B). 글 강제 삭제는 D-06 뒤.

## 12. UX 설계 기준

1. 첫 진입 시 예시 게시판과 **'게시판 추가'** CTA 제공.
2. 게시판 생성 시 어려운 옵션은 숨기고 **고급 설정**으로 분리.
3. 작업별 단계·현재 저장 상태·에러 이유를 명확히 표시.
4. 필드 빌더는 **왼쪽 편집 / 오른쪽 미리보기** 기본 화면 검토.
5. 삭제·타입 변경 같은 위험 작업은 영향받는 글 수를 안내.
6. 게시글 작성·수정 화면은 실제 사용자 사이트의 필드 순서와 유사하게 표시.
7. 키보드 사용·모바일 대응·명확한 레이블 등 접근성 고려.
8. 삭제 버튼만 강조하지 않고 비활성화·복제·복원 같은 안전한 대안을 배치.

## 17. 최종 권고

이 모듈의 핵심은 **'게시판을 하나 더 만드는 기능'이 아니라 고객이 스스로 콘텐츠 데이터 구조를 정의하고 운영하는 기능**이다. 초기 MVP에서는 아래 흐름의 완성을 최우선으로 한다.

> **게시판 생성 → 필드 구성 → 게시글 작성 → 홈페이지 배치/발행 → 안전한 수정·삭제·복원**

기존 CMS의 멀티 테넌트 아키텍처, 섹션 편집기, 방문자 인증, 파일 업로드, 공개 API를 재사용하되, **게시판 정의·게시글 데이터·권한을 독립 모듈로 분리**한다. 이렇게 하면 향후 공지사항·갤러리·FAQ뿐 아니라 프로젝트 포트폴리오, 채용 공고, 상품 소개, 업종별 맞춤 콘텐츠까지 같은 기반에서 확장할 수 있다.
